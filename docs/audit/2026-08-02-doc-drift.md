## D1 — critical. `e_blade`, `e_gurkha` and `e_hammer` are shimmed by two stages each

**Claimed.**

`ROADMAP.md:486`
> `e_blade`, `e_gurkha` and `e_hammer` have no shared implementation at all.

`ROADMAP.md:622-625`, under **Deliberately not doing**
> **Shimming `e_blade` or `e_gurkha`.** No stage shims them, so there is no
> shared implementation to defer to. Converting them would be wrong, not merely
> unhelpful. The index flags both.

`MATCHING-LESSONS.md:936-938`
> `shimmed_by == []` means there is no shared implementation to defer to.
> `e_blade` and `e_gurkha` are in this class, and converting them would be
> actively wrong, not merely unhelpful.

`automation/codebase_index.py:610-612` (`shim_viable` docstring)
> nothing shims it, so there is no shared implementation to defer to
> (e_blade, e_gurkha: shimmed_by == []).

**Actually true.** All three headers exist and each is shimmed by two stages
with a pure 3-4 line shim:

```
src/st/e_blade.h    <- src/st/no2/blade.c,  src/st/np3/blade.c
src/st/e_gurkha.h   <- src/st/no2/gurkha.c, src/st/np3/gurkha.c
src/st/e_hammer.h   <- src/st/no2/hammer.c, src/st/np3/hammer.c
```

`src/st/no2/blade.c` in full:

```c
// SPDX-License-Identifier: AGPL-3.0-or-later
#include "no2.h"

#include "../e_blade.h"
```

rno0 meanwhile carries private implementations: `e_blade.c` 120 lines,
`e_hammer.c` 119, `e_gurkha.c` 82, holding 2, 3 and 2 `INCLUDE_ASM` stubs
respectively. `src/st/e_blade.h` even calls `func_801CE1E8`/`func_801CE228`,
the two functions ROADMAP P3b (289-292) proposes moving *into*
`giantbro_helpers.h` — they are already consumed by a shared header.

**Why this is the worst finding.** It is stated three times, in the two
documents a new contributor reads first, in the section literally headed
"Deliberately not doing", and it is echoed by the tool's own docstring so a
reader who checks the code finds agreement. Seven stubs across three files are
currently ring-fenced as "converting them would be actively wrong".

**Not a claim that they *will* shim.** Blockers 2-4 still have to be checked
(rno0's `e_blade` segment is 0x1548 against np3/no2's, and the header may need
stage data). The defect is that the docs assert the *first* blocker, which is
false, and thereby stop anyone from checking the other three.

INCLUDE_ASM("st/rno0/nonmatchings/e_lock_camera", EntityLockCamera);

## D3 — critical. `shimmed_by` cannot see any shim whose filename differs from the stem

Root cause of D1 and D2, and it invalidates every count derived from it.

`automation/codebase_index.py:453`:

`../e_blade.h` from `blade.c` is invisible.

The 0x48 was split, the gain was `Update` + `UpdateStageEntities` matching, and

**`ROADMAP.md:241-255`** is the more damaging half. The "bss is now fully
attributed" table assigns `giantbro_helpers` **0xC4** at 0x54AC8 and concludes:

> **0x10 + 0xC00 + 0xC4 = 0xCD4, which is exactly the bss size the map reports.**
> The attribution closes with no gap and no overlap, so the proposed
> segmentation is arithmetically complete rather than a best guess

`giantbro_helpers` is 0x7C (0x54AC8..0x54B44), as both `ROADMAP.md:161` and
`config/splat.us.strno0.yaml:165-167` state — five static `s32` (0x14) plus

The arithmetic closing is therefore a coincidence of summing the *whole tail*
into one owner, presented as proof. This is exactly the failure the same section
warns about two paragraphs later ("splat sizes a symbol by distance to the next
label … Do not trust that number"). Worth an explicit retraction, because
"arithmetically complete rather than a best guess" is the kind of sentence that
stops the next person re-deriving it.
